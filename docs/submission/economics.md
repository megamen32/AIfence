# Экономика AIfence

Срез подготовлен 27 ноября 2026 года, UTC+5. Заявленная продуктовая модель
исполнения — **Terra fast**. Read-back слота также показывает MiniMax failover в
эффективном маршруте; это отдельное свойство runtime-маршрута, а не основание
придумывать второй checkpoint. Финальный прогон должен зафиксировать точный
model ID, сборку, число вызовов, токены и время; пока доступны только
исторические синтетические замеры и расчётный сценарий по датасету KES.

## Правило модели и месячная стоимость

Требование конкурса — open weights: модель должна допускать локальный запуск и
использование по открытой лицензии. Для самостоятельного размещения Terra fast
токены не являются отдельным счётом API: в калькуляторе `p_in = p_out = 0 ₽ за
миллион` только если подтверждён именно такой open-weights маршрут. Это не
означает нулевую стоимость эксплуатации: вычисления, память, Airlock, хранилище,
сеть и внешние интеграции считаются отдельно. Если финальный маршрут Terra fast
тарифицируется провайдером, нулевые ставки заменяются подтверждённым тарифом.

Для одного модельного прогона:

```text
C_model = (input_tokens × p_in + output_tokens × p_out) / 1 000 000
C_compute = compute_rub_per_hour × run_seconds / 3 600
C_run = C_model + C_compute + other_rub_per_run
```

Для месяца:

```text
C_month = infra_rub_per_month
        + chat_runs_per_month × C_run
        + watchdog_runs_per_month × C_watchdog_run
        + integration_rub_per_month
```

`infra_rub_per_month` включает выделенную долю Airlock, БД, объектного
хранилища и хоста модели. `integration_rub_per_month` включает только
подтверждённые расходы Redmine/UserIO/сети, которые не вошли в инфраструктурную
ставку. Общие расходы нельзя посчитать дважды. Неизвестное значение остаётся
`null`, а не превращается в ноль.

## Цена задержки: Kaspersky Endpoint Security

Источник — `Датасет_ИИ-помощник_PM_v17.xlsx`, лист **«Продажи»**, поле
`orders_index`, семейство **Kaspersky Endpoint Security**, только канал
самостоятельных заказов. В README датасета прямо указано, что значения — индекс,
а не абсолютное число заказов или рубли. Поэтому ниже рассчитана проверяемая
цена задержки в индексных единицах, а денежная сумма оставлена формулой.

| Окно | Полные недели | Средний индекс заказов |
| --- | ---: | ---: |
| 29.06–21.09, база перед релизом | 13 | **165,846** |
| 05.10–26.10, первые четыре недели после релиза | 4 | **113,000** |
| 05.10–16.11, весь доступный пострелизный срез | 7 | **111,571** |

Расчёт по коду из значений листа:

- первые четыре недели: `113 / 165,846 − 1 = −31,865%`;
- весь семинедельный срез: `111,571 / 165,846 − 1 = −32,726%`;
- накопленный дефицит за семь недель относительно базы: `379,923` индексных
  пунктов, то есть `3,799231 × B`, где `B` — неизвестное абсолютное число
  самостоятельных заказов в базовую неделю;
- если сигнал замечен после первых четырёх полных недель, а реакция отложена
  до недели 16.11, дополнительные три недели дают `168,538` индексных пунктов,
  или `1,685385 × B` потенциально недополученных самостоятельных заказов.

Контроль Astra Linux за те же окна изменился с 98,538 до 96,000, то есть на
`−2,576%`; это поддерживает проверку, что провал KES не равен общей динамике
витрины. Это не доказывает причину падения.

Денежная цена этой задержки может быть посчитана сразу после получения двух
отсутствующих входов:

```text
late_cost_rub = 1,685385 × B
               × contribution_rub_per_order
               × recoverable_fraction
```

Для всего семинедельного окна коэффициент `1,685385` заменяется на `3,799231`.
В датасете нет `B`, цены без налога, переменных затрат и подтверждённой доли
предотвращаемого падения, поэтому утверждать сумму в рублях или ROI нельзя.
Индексный результат — фактический value proxy из данных, а не придуманная
денежная оценка.

## Рублёвый калькулятор в терминах заказчика

Калькулятор переводит тот же измеренный процент падения в вклад, который мог
быть потерян из-за позднего обнаружения. Он явно разделяет наблюдение и
допущения:

| Вход | Смысл | Статус для KES |
| --- | --- | --- |
| `orders_per_week` | самостоятельные заказы в обычную неделю, шт. | нет в обезличенном датасете |
| `average_check_rub` | средний чек одного заказа, ₽ | нет в обезличенном датасете |
| `margin_pct` | маржа после переменных затрат, % от чека | нет в обезличенном датасете |
| `failure_drop_pct` | доля падения заказов | **измерено: 32,726%** по индексу KES выше |
| `first_detection_after_weeks` | сколько недель потерь остаётся, если нашли в первую неделю | допущение сценария |
| `late_detection_after_weeks` | сколько недель потерь остаётся при позднем обнаружении | допущение сценария |
| `preventable_fraction` | доля дополнительной потери, которую ранняя реакция могла бы предотвратить | допущение сценария, от 0 до 1 |

Формулы:

```text
weekly_failure_cost = orders_per_week × average_check_rub
                    × margin_pct / 100 × failure_drop_pct / 100
cost_if_found_first_week = weekly_failure_cost × first_detection_after_weeks
cost_if_found_late = weekly_failure_cost × late_detection_after_weeks
late_detection_penalty = weekly_failure_cost
                       × (late_detection_after_weeks - first_detection_after_weeks)
                       × preventable_fraction
```

### Пример с явными допущениями

Это **не измерение Softline**. Для иллюстрации принято: `100` заказов в
неделю, средний чек `50 000 ₽`, маржа `20%`, измеренное падение `32,726%`,
обнаружение в первую неделю против обнаружения через четыре недели, а доля
предотвращаемой дополнительной потери равна `100%`.

```text
weekly_failure_cost = 100 × 50 000 × 20% × 32,726% = 327 260 ₽
found_in_week_1      = 327 260 × 1 = 327 260 ₽
found_in_week_4      = 327 260 × 4 = 1 309 040 ₽
late_detection_cost  = 327 260 × (4 − 1) × 100% = 981 780 ₽
```

В этом сценарии `981 780 ₽` — стоимость трёх дополнительных недель задержки
при заданных допущениях. Она не должна показываться как фактический финансовый
эффект, пока заказчик не передаст абсолютный объём заказов, средний чек и
маржу.

## Входы для финального калькулятора

Заполнять только после замера Terra fast и согласования экономики. Файл
остаётся в игнорируемом `data/`:

```json
{
  "input_tokens": null,
  "output_tokens": null,
  "input_rub_per_million": 0,
  "output_rub_per_million": 0,
  "compute_rub_per_hour": null,
  "run_seconds": null,
  "other_rub_per_run": null,
  "runs_per_week": null,
  "baseline_orders_per_week": null,
  "observed_orders_per_week": null,
  "contribution_rub_per_order": null,
  "weeks_earlier": null,
  "recoverable_fraction": null,
  "orders_per_week": null,
  "average_check_rub": null,
  "margin_pct": null,
  "failure_drop_pct": 32.726,
  "first_detection_after_weeks": 1,
  "late_detection_after_weeks": 4,
  "preventable_fraction": null
}
```

`0` для ставок токенов допустим только после подтверждения open-weights
маршрута; неизвестные вычисления, объём заказов, средний чек и маржа остаются
`null`. Поля рублёвого калькулятора возвращают `null`, пока не заполнены все
явно перечисленные входы.

```sh
python3 docs/submission/economics.py data/economics-input.json
```

Калькулятор возвращает `null`, если нельзя обосновать стоимость или денежный
эффект всеми необходимыми входами. Методика повторного замера описана в
[economics-handoff.md](economics-handoff.md).
