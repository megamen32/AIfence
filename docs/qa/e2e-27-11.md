## Frozen run script

Run this sequence as the owner on the current committed stand. Keep the chat
request vague; configure the watcher as a separate operator action.

1. Record the deployed application revision, stand health, local time in
   UTC+5, and the current `/delivery` page. Capture one screenshot before any
   mutation. Keep the existing chat and browser tabs owned by other agents
   untouched.
2. In a fresh owner chat, send exactly:

   ```text
   эээ, слушайте, по Касперскому как-то продажи просели вроде? или мне кажется. посмотрите, что там, и если что-то серьёзное, скажите, что делать
   ```

   Record the chat URL, start/end timestamps, the tool receipts shown by
   Airlock, the final answer, and a screenshot after completion. Grade whether
   the agent found the product, window, cause and confidence without those
   facts being in the request.
3. In a separate owner operation, enable the weekly source watch with the
   first UTC Monday `2026-11-23`. Use only the exact read-only bindings shown
   for this owner in the live Airlock profile. The store metric is orders and
   the threshold is the configured acceptance threshold; include only the
   additional owner-bound demand, trends, or market sources that are actually
   configured. Do not copy binding UUIDs into this document or into chat.
   Record the start request, the returned `watch_id`, the stored configuration,
   and the enqueue receipt. The initial Monday is already in the past, so the
   first check must be observed as an immediate run.
4. Wait for the `check_source_watch` occurrence for Monday `2026-11-23`.
   Inspect the watch summary once, then inspect its review only after an
   `analysis_run_id` or a terminal no-review status exists. Record the
   occurrence `signal_id`, status, warnings, `analysis_run_id` if present,
   review result, evidence IDs and timestamps. Capture a screenshot of the
   completed review. A missing owner-bound app read, missing review route,
   unsupported status, or a review without a pinned signal is a failure, not
   a successful quiet run.
5. Open `/delivery` in a session-owned tab and capture its waiting state. Click
   `Сверить сейчас` once. Record the HTTP outcome shown by the page, the first
   Redmine issue ID and URL, the exact signal ID, and the AI-generated flag.
   Open the issue and capture a screenshot showing the flag and signal field.
6. Click `Сверить сейчас` a second time. Record the returned issue list and
   compare it with the first result. The same owner/signal pair must return
   the same issue ID and must not create a second issue or an extra journal
   entry. Capture a screenshot of the second result.
7. Click `Отправить сейчас` once. Record the Dion day, configured test chat
   check, draft ID, `sent` state, `delivery_confirmed`, `delivery_status`,
   and the durable UserIO receipt from the job/MCP result. The page's
   `отправлено` label alone is insufficient proof of a receipt. Capture the
   delivered state. Repeat the action once and verify that the same receipt is
   replayed without another message.
8. After the code-freeze revision is deployed at `00:00` UTC+5, repeat steps
   1, 3–7 with a new run key. Do not reuse the first chat, watcher, signal or
   receipt. Record the exact frozen commit and target runtime for this second
   result.

### Mechanical evidence checklist

For each phase record `started_at`, `finished_at`, stand URL, commit, browser
profile, screenshot path/receipt, and the relevant durable ID. Do not record
cookies, tokens, one-time URLs, browser leases or binding UUIDs.

| Phase | Required evidence |
|---|---|

| Watch start | `watch_id`, stored Monday, configured sources, enqueue/job receipt |
| Watch review | `signal_id`, status, `analysis_run_id`, warnings, evidence IDs, screenshot |
