# Конкурентный анализ: агент собирает сам — ТЗ для Олега (26.11, версия 2)

## Главное

Данные для решения агент собирает **сам**, по расписанию и по сигналу. Таблица заказчика `Store_Конкурентное_исследование.xlsx` нужна не как вход, а как **ответ для проверки**: агент собирает те же ячейки сам, а мы сравниваем его результат с ручным исследованием их аналитиков. Это та же идея, что и слепые сценарии: «агент за N минут повторил X% их ручной работы, вот расхождения».

Что сказала заказчица на кик-оффе 26.11: «помощник, который умеет заходить, вытягивать, анализировать данные из Яндекс.Метрики, накладывать на него конкурентный анализ»; «в идеале сравнение продуктовой карточки, её цены, как она представлена у ключевых конкурентов — в автоматическом режиме, чтобы мы гибко реагировали»; конкурентный анализ «релевантен в любой задаче». Организатор: обязательна только интеграция с Метрикой, трекер можно заглушкой.

## Состав: 4 части вместо 6 модулей (решение по ТРИЗ)

ИКР: матрица заполняется сама при обходе, который агент и так делает (проверка пути покупки Store уже ходит Playwright по сайту). Противоречие: модуль анализа должен быть, чтобы оценивать десятки критериев, и не должен быть, чтобы не писать код под каждый. Разрешение: критерии становятся данными, а анализ остаётся один.

1. **Провайдеры (адаптеры, не модули)**: `search(query) → [url, позиция, сниппет]` и `demand(query) → частота`. Реализации меняются в настройках: SearXNG в своём контуре, Yandex Search API, Wordstat по ключу, TinyFish или иной облачный провайдер. Без ключа ответ «не подключён». Поиск конкурентов — не модуль, а функция поверх `search`: домены в TOP-10 по коммерческим запросам продуктов Store, пересечение считает код (так собран их лист 0).
2. **Один сборщик — снимок страницы**: URL → HTML, скриншоты (десктоп, мобильный), сетевые события, шаги до корзины, время загрузки. Расширение существующего path-check на чужие домены. Для цены быстрый путь — существующие парсеры Market Watch.
3. **Одна рубрика**: блоки, критерии и веса из листа «Итоги» как конфиг. У каждого критерия тип извлечения: `code` (индекс цены, число шагов, есть ли поле), `vision` (модель оценивает скриншот по формулировке критерия), `manual` (человек или их таблица). Новый критерий = новая строка конфига, без кода. UX, карточка, покупка — это строки рубрики, а не отдельные модули.
4. **Сторож изменений** — не новый модуль, а второй детектор в том же цикле сторожа (расписание → наблюдения → детектор → дедуп first-seen → письмо → карточка). Правило изменения задаётся в строке рубрики: число (порог и подтверждение вторым снимком), да/нет (флаг переключился), набор (поле есть у конкурентов и нет у Store). Сигнал в общем контракте, карточка и письмо не знают источника. Самопроверка по их таблице — тест приёмки, как скорер слепых сценариев, а не модуль.

Приёмы: универсальность (один обход даёт все блоки), посредник (провайдер поиска за интерфейсом), вынесение (дорогая модель только на `vision` и только по сигналу), предварительное действие (ежедневный дешёвый обход, анализ по сигналу), самообслуживание (агент сам меряет свою точность по эталону).

## Как устроено (одно приложение)

Модуль внутри Product Manager, без нового приложения и без второго оркестратора.

1. **Матрица**: конкурент × блок × критерий → значение, балл, источник (`собрано агентом` / `из исследования заказчика` / `не собрано`), дата, URL или скрин. Веса из «Итогов», взвешенный балл считает код.
2. **Сборщики как инструменты агента**: цена, карточка, путь покупки и UX, поиск. Агент сам решает, что и у кого собрать: по расписанию обходит TOP-конкурентов по ключевым продуктам, а по сигналу сторожа (например, просел KES) сразу собирает свежие данные по этому продукту.
3. **Сверка с ручным исследованием**: отчёт «собрано агентом vs их таблица» по каждой ячейке, процент совпадения, расхождения с объяснением (цена изменилась с даты их проверки, другая редакция и так далее).
4. **Сигнал изменений**: конкурент снизил цену, добавил онлайн-счёт, в карточке Store не хватает поля, которое есть у всех конкурентов. Изменение идёт в карточку гипотезы как свидетельство с отметкой «за / против / неизвестно».
5. **Модель тонкая**: решает, что собрать, сравнивает списки полей, оценивает скриншот и пишет вывод. Числа, баллы и совпадения считает код.

## Связь с ядром и кейсом KES

Кейс KES — заказы уходят из корзины к менеджеру. Агент сам собирает: у кого из конкурентов KES покупается без менеджера, сколько шагов, какие поля в карточке есть у них и нет у Store. Это прямой материал для гипотезы «в описании не хватает данных, поэтому идут к менеджеру», и он появится в карточке как контекст, а не как доказанная причина.

По их же матрице Store уже лидер по взвешенному баллу, а разрывы в основном в поиске и рекламе. Поэтому ценность в постоянном слежении и реакции на изменения, а не в разовом отчёте.
