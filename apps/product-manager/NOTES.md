Нативное приложение владельца продукта. Рабочее состояние находится в изолированном Postgres Airlock. Локальный бэклог хранит подтвержденные задачи. Порог улучшения на 10 п.п. относительно контроля и 28 дней в сценарии индекса заказов являются редактируемым предложением команды. Запуск и приемка описаны в README.md.

Еженедельная проверка `sourcewatch` использует нативную очередь Airlock. Владелец включает её вручную инструментом `start_source_watch`; при деплое ничего не запускается автоматически. Конфигурация хранит привязку `metrika-analyst.compare_periods` для показателя магазина и одну или несколько дополнительных привязок: `compare_demand` (Wordstat, количество запросов), `compare_google_trends` (относительный интерес 0–100 по одной нормировке) и `market-watch.price_week_delta` (двухнедельная дельта цены по серии сравнимых предложений одного SKU). Проверка сравнивает две последние полные недели с понедельника по воскресенье по UTC. В `Check` передаются фиксированные параметры, поэтому выбор файлов и произвольные коннекторы из задания исключены. Значения и локаторы берутся из ответа источника; приложение не пересчитывает дельту цен и не группирует сырые предложения.

Область проверки. Пустой `product_key` оставляет действующий live-store путь: `product_key=store` и provenance `yandex-metrika:<число>`, владелец и привязка проверяются как раньше. Явный `product_key` с необязательным `segment` включает чтение явно маркированного продуктового снимка. `Check` предпочитает уже готовый `relative_change_pct` от Metrika для этого же продукта, сегмента и окна. Если его нет, считает две полные недели из сырых `observed`-рядов той же семьи, сегмента, источника и ревизии. Семейный ряд никогда не превращается в `store`, ID счётчика не выдумывается. В сигнал попадают оба исходных наблюдения с их ID, локаторами, единицей и `synthetic`-происхождением; оба ID допустимы как evidence для `review_source_signal`.

Цены по семейству. Точная настройка `sku` читает `price_week_delta` для одного артикула, как раньше. Вместо неё можно задать `skus` (1–20 явных артикулов) или `family` (фраза 4–200 знаков для обнаружения по индексированным названиям); оба варианта взаимоисключающие и требуют привязки рынка. В этом режиме `Check` вызывает `market-watch.family_price_week_delta` и получает сравнимые двухнедельные дельты по нескольким SKU, их evidence ID, точные полные недели и покрытие (`price_coverage`). Каждая серия остаётся внутри одного SKU, продавца, URL, валюты, базиса цены и уровня количества. Рубли разных лицензий и артикулов не усредняются: в `price_families` лежит отдельная запись с собственными исходными ценами и процентом. Несопоставимые условия не становятся изменением цены, их ID недоступны для `review_source_signal`. `Check` сверяет недели ответа с запрошенными и отвергает расхождение.

Сводка чата `review_sales_and_prices`. Раньше она наследовала режим панели и отбрасывала все явно маркированные синтетические наблюдения, поэтому владелец с импортированными рядами получал пустой ответ без объяснения. Теперь сводка читает наблюдения владельца как есть: если есть реальные ряды, демо-дубли к ним не подмешиваются, а чисто синтетический набор не скрывается. Поле `data_state` показывает число снимков, наблюдений, продуктов, строк `watchdog.alert`, признак `labelled_synthetic` и следующий шаг. Отдельно исправлено имя измеряемого продукта: сигнал сторожа хранит артикул в `product_key`, поэтому семейство цели берётся из локаторов самой целевой серии в `source_refs`, без выдумывания и без подстановки контроля.

Для Wordstat и Trends `Check` требует ровно два наблюдения `observed` по точной фразе за две запрошенные недели, общий источник и одну нормировку. Опубликованный ноль считается числом. Явный `unavailable` от Вордстата с актуальной датой не скрывает достигнутое пороговое падение Метрики, а попадает в разбор как отсутствие спроса. При спокойной Метрике такая проверка получает статус `incomplete`.

`review_source_signal` — типизированное задание (`ReviewInput → ReviewOutput`: `hypothesis`, `evidence_ids[]`, `missing[]`, `test{metric,threshold_pct,days}`). Валидатор отвергает любой `evidence_id`, которого нет в закреплённом сигнале. Разбор запускается только по явно подтверждённому владельцем маршруту `source_watch_analysis_route=approved` и только при достигнутом пороге.

Черновик Redmine отложен до контрольной точки 16:00. Доменная логика `Approve` (идемпотентный черновик по `signalID` и evidence IDs) сохранена в пакете `sourcewatch`, но изменяющий инструмент `approve_source_signal` и HTTP-действие `POST /source-watch/approve` в релизный срез не регистрируются. В реальный трекер ничего не отправляется; задачу не предодобряет ни чат, ни инструмент.

Нативная сборка использует закреплённые версии личного SDK и Sol через scripts/personal-build-apps.py. Задание читает только операции, явно привязанные владельцем к check_source_watch@1; HostSupportsAppRead=true. При повторной доставке сохраняется исходный сигнал и его идентификатор, проверка evidence IDs входит в нативный review. Ошибка дополнительного источника сохраняет независимый подтверждённый сигнал и возвращает предупреждение без деталей провайдера. Инструмент rebind_source_watch заменяет только binding IDs существующих источников своего владельца через JSON patch с проверкой исходной конфигурации. watch_id, очередь, активность и история не меняются.

## Конкурентный анализ MVP
- Product Manager теперь регистрирует plan_competitor_research и export_competitor_csv.
- План принимает компанию, сайт, рынок, предложение, цель и необязательные конкурентов/товары; пустые списки остаются пустыми, чтобы агент сначала выполнил поиск.
- CSV детерминированно сортирует строки и хранит URL, дату, статус и заметки. missing/unknown не превращаются в нули.
- В chat экспорт прикрепляется как competitor-analysis.csv в conversation-scoped storage на 72 часа.
- Поиск, браузер и Market Watch подключаются через инструменты/адаптеры агента; формы конкурентов не отправляются.

## Доставка в Redmine и Dion

Запись в системы заказчика запускает только кнопка владельца в панели. Чат и инструменты модели до неё не достают: межприложенческие привязки ядра Airlock разрешают только операции `ReadOnly`, поэтому PM пишет через собственные штатные подключения, а ключи хранит Airlock.

- **Redmine.** Подключение `redmine` (API-ключ служебного пользователя «ИИ помощник», заголовок `X-Redmine-API-Key`), проект из `redmine_project`, ссылки по `redmine_public_url`. Кнопка «Создать эту задачу» сначала создаёт локальную задачу, затем задачу Redmine в трекере «Улучшение»: тема `[ИИ] <заголовок> [<ID сигнала>]`, в описании цифры до/после из проверенного окна сигнала, контроль, критерий успеха и все evidence ID. Поля «Сгенерирована ИИ-помощником» = да и «ID сигнала» ставятся, если они подключены к проекту; иначе метка остаётся в теме и описании. Идемпотентность по владельцу и ID сигнала: локальная квитанция `pm_redmine_issues`, при её потере — поиск в Redmine по полю «ID сигнала». Сбой Redmine не отменяет локальную задачу: карточка ведёт на `/delivery` с кнопкой повтора.
- **Dion.** MCP `userio` (UserIO, личный токен владельца, `BindingPerUser`). Задание `prepare_morning_dion` в 09:00 UTC+5 выбирает главное отклонение (наибольший |relative_change_pct| среди проверенных окон сигналов), готовит в UserIO черновик `userio.messages.prepare` для чата из `dion_test_chat` и ставит себя на следующее утро. Включается кнопкой на `/delivery`. Отправка — только кнопкой «Отправить в Dion» через `userio.messages.send` с точным снимком (`draft_id`, текст, чат, пустые вложения). Черновик другому чату не отправляется; повторное подтверждение не шлёт второй раз.
