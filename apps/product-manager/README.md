# Product Manager

Приложение Airlock для продуктового решения. В карточке видны сигнал, источники, альтернативные объяснения, предлагаемая проверка и условие успеха. После подтверждения появляется одна задача локального бэклога. Метрика и правило фиксируются перед отправкой, а измерения после релиза можно добавить позднее.

## Запуск на Mac M1

Локальный Airlock из корня проекта должен работать на http://localhost:42080. Используются Go 1.26.11 и Agent SDK v0.11.0, штатная сессия Airlock CLI и собственная схема PostgreSQL приложения.

```sh
cd /Users/user/AIfence/apps/product-manager
go tool air toolchain install
go tool air build
go tool air login http://localhost:42080
# Только для первого развёртывания в новом Airlock
go tool air deploy --create --name 'Product Manager' --slug product-manager -m 'Install Product Manager' --wait
# Для обновления привязанного приложения
go tool air deploy -m 'Update Product Manager' --wait
go tool air status --json
```

Для встроенной панели локального стенда после общего запуска один раз выполните из корня AIfence `./apps/product-manager/ops/enable-local-iframe`. Команда идемпотентно добавляет только адрес этого приложения в существующее локальное правило сессий iframe. После перезапуска общего прокси ее можно выполнить повторно. На других установках используется штатный URL Airlock.

Адрес формы и рабочего пространства берите из полей routeBaseUrl и workspaceUrl команды status. Человек работает под своей учетной записью Airlock, отдельный вход для приложения не требуется. Импорт, пересчет и создание предложения в закрытом контуре выполняет одна команда.

```sh
python3 sync_case.py
```

Она заново читает оригиналы из папки материалов, исключает эталон, сохраняет производный JSON за пределами исходников и вызывает штатные маршруты подписанным клиентом. Полные недели и неполная последняя неделя считаются отдельно. Повторное выполнение для неизменного источника возвращает тот же снимок и карточку. При совпадении продукта, метрики и базы повторный разбор возвращает ранее сохраненное решение, в том числе последнюю версию правок пользователя. Ответ команды содержит отдельно новый и привязанный к карточке идентификаторы снимков. Подробное описание отбора данных и источников находится в research/README.md.

## Работа с карточкой

Откройте снимок. Кнопка «Разобрать изменение заказов» сохраняет предложение по самому сильному снижению среди сопоставимых полных недель. Это детерминированный сценарий для индекса семейства. Другие метрики и гипотезы можно исследовать в чате по нормализованным наблюдениям. Карточка сохраняет стабильные ID проверяемых данных. Форма позволяет открыть строки, изменить формулировку и критерий, затем явно подтвердить задачу. Одновременное изменение версии обнаруживается. После подтверждения фиксируются выбранные критерии. Ссылка на задачу открывает ту же карточку и ее запись в локальном бэклоге. Задача хранится в локальном прототипе бэклога.

На демонстрационном Mac наблюдатель обрабатывает измененные файлы и проверяет их каждые три часа. Сверка по содержимому пропускает неизменившиеся файлы. Смена входных данных создает новый снимок. Отредактированное решение сохраняет исходную привязку до пересмотра человеком.

Из папки приложения `python3 ops/watch_cases.py install` подключает наблюдатель к текущей графической сессии Mac. После нового входа в macOS повторите эту команду. `python3 ops/watch_cases.py status` выводит последнюю подтвержденную обработку.

## MCP и общие данные Airlock

| Инструмент | Назначение |
|---|---|
| list_evidence, read_evidence | Найти доступные снимки, прочитать наблюдения с фильтрами и пагинацией |
| import_evidence | Импортировать evidence-v1, архив наблюдений или результат общего workflow |
| investigate_orders | Сохранить карточку для наблюдаемой тревоги сторожа или разобрать старый снимок с полными неделями |
| save_hypothesis, get_hypothesis, list_hypotheses | Записать, открыть и найти карточку с текущей версией |
| send_to_backlog | Прочитать квитанцию задачи, отдельно подтверждённой в панели |
| get_product_focus, set_product_focus | Прочитать или выбрать продукт для панели текущего пользователя |
| evaluate_hypothesis | Проверить результат по ранее выбранной метрике, периодам и контролю |

Для свежих данных подключенные приложения предоставляют свои авторизованные MCP-инструменты. Штатный workflows/collect-evidence.js формирует общий документ через пользовательский каталог Airlock. Прочитайте этот файл в авторизованном workflow и передайте JSON в import_evidence. Маршруты /import, /investigate, /edit, /approve предоставляют те же основные операции через локальную форму. Только авторизованный пользователь видит свои записи. Одинаковое содержимое получает постоянный идентификатор ev-<sha256>.

Исторический импортер помечает клиентский снимок local_project_only. В обычной настройке закрытые наблюдения, карточки и производные задачи доступны человеку в локальной форме. На стенде это позволяет разбирать исходные документы без передачи их модели. Если владелец уже настроил согласованный для этих данных маршрут модели, настройка приложения private_model_route=approved разрешает доступ в штатном авторизованном чате после перезапуска приложения. Это утверждение оператора о действующем маршруте. Само приложение маршрутизацию модели не меняет.

## Сторож и проверка пути

Для общего вопроса чат изучает доступную историю и выбирает продукт, окно, метрику и контроль по наблюдениям. После найденной тревоги он сохраняет карточку, показывает предложение и сразу даёт ссылку на карточку. Единственное подтверждение — кнопка **«Создать эту задачу»** на актуальной карточке. Чат затем может прочитать квитанцию. Успешное расследование выставляет фокус продукта владельца и обновляет панель.

Для уже импортированного снимка `investigate_orders` принимает необязательные `product_key` и `week_from` (понедельник ISO). По умолчанию выбирает последнюю наблюдаемую тревогу среди подходящих недель. `watchdog.alert=false`, неполные и несопоставимые периоды пропускаются. При наличии результатов сторожа устаревший сигнал индекса не подменяет отсутствие тревоги. ID карточки стабилен для одного ID сигнала, разные недели дают разные карточки. В снимках с несколькими неделями `watchdog.alert` фильтр «Прогон по истории» показывает переданные решения, динамику и причины.

Карточка сохраняет критерий на базе полного текущего окна сигнала, контекст выпуска, бэклога, разрывов учёта и прочие наблюдения из снимка. Результат пути связывается по точному ключу продукта. `path_verified` требует наблюдаемого `browser/path_check` со значением `path_broken`, `metrika_add_not_observed` или `ok`. В карточке датируется сама проверка пути. Для обоснования исторической причины потребуется отдельное измерение.

Интерфейс отправляет авторизованный `POST /approve` с `Content-Type: application/x-www-form-urlencoded` относительно `routeBaseUrl` PM. Поля формы — `id` сохранённой гипотезы, `version` текущей версии показанного черновика и `confirmed=yes` из нажатой кнопки. Версию берите из скрытого поля формы или из верхнего поля `version` в ответе `get_hypothesis` перед подтверждением. Если черновик изменился, откройте карточку заново. Успешный POST возвращает перенаправление на карточку, а повтор возвращает ту же сохранённую задачу. Каждый принятый ключ закрепляется за карточкой в области владельца. Чтобы добавить браузерный результат к черновику, импортируйте объединённый снимок с исходными ссылками. Повторный разбор сохраняет уже подтверждённый результат пути. Утверждённый критерий остаётся связан с задачей.

## Уведомления

По умолчанию `signal_notifications=off`. Включайте `signal_notifications=bridge` после настройки разрешённого Airlock bridge. Владелец подписывается на `product_signals` из своего канала. Новый наблюдаемый сигнал вызывает одну попытку публикации на владельца и набор исходных ID. Ссылка ведёт в карточку с обычной авторизацией Airlock. Ответ SDK без подтверждения доставки не повторяется автоматически. Почтового отправителя настройка не добавляет.

## Оценка результата

Количество дней, исходный период, метрика, контроль и правило заранее сохраняются в карточке. Для полного числа недель окно открывается с первого понедельника после выпуска. Для прикрепления выпуска нужен новый снимок с наблюдением release и полем details.hypothesis_id. Для замеров укажите ID фактических baseline/current и контрольных наблюдений. У них должны совпадать метрика и сегмент, в details должны быть complete=true, quality=comparable и measurement_kind=product_outcome. Отсутствие полных данных оставляет awaiting_measurement. Исправление регистрации событий можно пометить measurement_repair. Проверки не будут засчитаны как изменение продуктового результата. Подтвержденное или отклоненное решение сохраняется вместе с четырьмя ссылками при наличии контроля.

## Приёмка

```sh
go tool air build
python3 -m unittest discover -s research -v
python3 qa/acceptance.py
```

Для интерактивной приёмки `--prepare-chat` выдаёт только исходный вопрос. Перед подтверждением проверьте карточку через `--check-chat <ID>`, после одного нажатия кнопки в панели используйте `--check-confirmed <ID>`. Фикстуры учебные, исходные материалы и реальные данные заказчика остаются вне Git. Код разбора использует стандартную библиотеку Python. Приложение использует существующие Go SDK, UI и библиотеки из go.mod.
