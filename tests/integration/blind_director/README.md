# Слепой прогон вопросов директора

Статус: подготовка; живые чаты запрещено запускать до установки и проверки native discovery инструмента B и согласования указанного ниже контракта. `questions.json` фиксируется до распределения наборов. Вопрос не содержит подсказки к скрытому ответу; случайная независимая перестановка вопросов сохраняется до запуска. Без запуска чатов эти материалы не являются приёмкой.

## Подготовка

```sh
GOMAXPROCS=2 GOFLAGS=-p=1 python3 tests/integration/blind_director/harness.py prepare
```

Каждый запуск создаёт шесть наборов в `.runtime/blind-director/run-…/inputs/case-NN`; оракулы и truth находятся в соседнем `vault/`, вне всех пользовательских каталогов Airlock. Выбираются пять классов и случайно один повтор, классы случайно распределяются; оператор не читает vault. Из исходной Метрики удалён seed, из manifest удалён seed hash, чтобы не восстановить ответ из исходного кода генератора. Зафиксированы хеши входов, вопросов, генератора, скорера и harness; локальные копии генератора и скорера сохранены в `tools/` запуска, чтобы параллельные изменения исходников не меняли оценку. Запрещено монтировать корень run или vault, использовать один общий доступный каталог, публичные ссылки и копировать hidden answers в приложение.

## Контракт для B и интегратора до старта

- Действующая схема и имена native discovery/read tools, конкретный Airlock app/route, зарегистрированные права текущего пользователя, стабильные source locators, формат ошибок/неполных данных и различение синтетики от live. Проверить одним независимым техническим canary, не выполняя шесть вопросов.
- Изолированный кабинет или workspace с доказуемой идентичностью. Операция установить **один** active dataset по каталогу `inputs/case-NN`, атомарно переключить его между случаями, удостовериться какой input/version фактически увидит B. Никакой `vault`, других случаев, эталона, личной памяти, импортированного контекста или старого чата в области видимости. Необходимы точные формы входа `metrika.json`, `Продажи.xlsx`, `releases.json`, `backlog.json`, способ загрузки и сквозной контракт преобразования в evidence: формат, ограничения, единицы, пустые поля, период и источники. Недоступное сообщать, не подменять.
- Подтверждённый live chat transport: создание шести независимых новых разговоров, ID, передача только соответствующего исходного вопроса и полное сохранение ответа и окончания/ошибки без модификаций; подтверждение только отдельным нажатием на конкретной карточке при явной просьбе агента. Второй turn с текстовым «да» запрещён.
- Read-only backend route для полного списка ID задач конкретного кабинета до первого ответа, сразу после первого и после второго turn, с source locator/временем, отсутствием пагинационных пропусков и однозначной связью с запросом. Один только текст чата не доказывает отсутствие задачи. При отсутствии доказательства значение неизвестно, а не pass. Проверить выделенный кабинет и доступ к нему до любого чата.
- Точная семантика карточки: если в живом ответе нет явно указанных семейства и недели, нормализация оставляет значение неизвестным. Схема ответа не внедряется в вопрос директора. Потребуются исходные сообщения, идентификатор чата и независимые подтверждения route/backend. Любое сопоставление требует фиксированного парсера, без ручной расстановки полей после просмотра ответа или оракула.

## Фиксация и оценка

Адаптер `live_adapter.py` подготовлен по локальным исходникам API; работа со стендом не проверена. После подтверждения B/C выполните один smoke на отдельном синтетическом входе до запуска шести запросов. Не используйте тестовую учётную запись с существующими карточками для приёмки без согласованной изоляции. Для каждого случая он пишет закрытый JSON `record.json` с `case`, точным `question`, уникальным `chat_id`, дословным `first_response`, `first_status` (`completed`, `failed`, `timeout` или `unknown`), `second_request` (точно «Хорошо, поставь эту задачу.» или null), `second_response` (строка или null), списками `task_ids_before`, `task_ids_after_first`, `task_ids_after_second`, независимыми `transport_evidence` и `backend_evidence`. Доказательства содержат ссылки на приватные неизменяемые артефакты, не секреты. Пустые доказательства означают неполноту. Внутренние snapshots/маркеры должны подтверждать active dataset и новый чат.

```sh
python3 tests/integration/blind_director/harness.py freeze --run <run> --case case-01 --record <private-record.json>
# Повторить для всех шести, до вскрытия оракула.
python3 tests/integration/blind_director/harness.py score --run <run>
```

Freeze проверяет хеши, неизменяемо сохраняет raw запись и запрещает заранее подставлять normalized поля. Score требует все шесть записей и шесть разных чатов, фиксирует нормализацию локально до чтения vault, затем сравнивает family/week/cause с oracle. Номер недели генератора переводится в дату относительно 2026-01-05. Неизвлекаемый результат, ошибка, тайм-аут или пустой ответ = unscorable. Тихий вывод засчитывается только при завершённом ответе, однозначной формулировке и ссылке на существующее наблюдение именно этого набора; противоречивый текст остаётся unscorable. Агрегат отдельно сообщает непроверенные критерии. Достоверность ссылок на источники, обоснованность причинности, качество задач и действительность evidence требуют независимой проверки; их наличие в файле само по себе ничего не доказывает.

Скорер sibling по умолчанию сравнивает номер недели генератора со строковой датой и может не оценить естественный ответ; также его текстовый fallback не равен надёжному разбору семантики. Здесь используется фиксированный `card_fields` этого скорера только как синтаксический парсер и отдельное строгое сравнение; причину или цель без явно извлечённых полей не угадываем. Нужны дополнительные структурированные данные от B, иначе результаты будут честно `unscorable`.

## Подтверждение задачи

Первый ответ должен содержать явное обращение к человеку; само появление карточки действия не запускает. Неоднозначная просьба не вызывает действие. Текстовое «да» не отправляется; просьба подтвердить только текстом фиксируется как неподдерживаемая ветка.

Для интерфейса адаптер считывает карточку `GET /?id=…` и проверяет, что показана единственная форма `POST /approve` с точными `id`, `version` и кнопкой «Создать эту задачу». Затем необходимо **одно** реальное нажатие в браузере под владельцем карточки и фиксация 303, карточки до/после и прочитанной квитанции с тегом. Повторный POST проверяет идемпотентность, а не является вторым согласием. Запись `confirmation-before.json` содержит подготовленные ID, версию и параметры формы.

Пока browser transport изолированной учётки не реализован, UI-ветка останавливается до действия. Прямой HTTP POST не выдаётся за browser click. Без этой части нельзя объявлять завершённым случай, для которого агент попросил подтвердить на карточке.

## Остановка отправок и предохранитель QA

Тестовые user prompts в реальный Airlock отправляет только владелец. `live_adapter.py` допускает live-режим лишь с `--owner-send`; до любых сетевых действий и непосредственно перед отправкой вызывается один `prompt_guard.require_prompt`. Он механически проверяет признаки из `.agents/skills/qa-testing/SKILL.md`. Это фильтр известных формулировок, а не доказательство семантической чистоты: оставшуюся неоднозначность проверяет владелец. Нельзя переписывать вопрос после неудачи модели ради прохода.

**Настоящий price acceptance:** режим `--purpose price_acceptance --smoke --prompt-file <файл>` принимает только точное посимвольное совпадение с константой `PRICE_ACCEPTANCE` в `prompt_guard.py`: `слушайте, может нам цену на Касперского снизить? продажи вроде упали, конкуренты наверное дешевле`. Регистр, пробелы и знаки не нормализуются. Обычный режим `director` допускает другие естественные вопросы о цене, но не приравнивает их к этому acceptance.

Per-case Keychain отсутствует. `token_client.py` обращается только к защищённому `.runtime/blind-director/login.sock`, проверяет владельца и режим каталога/сокета, а на macOS также UID peer. Однопроцессный `token_broker.py` читает один раз уже выданные токены из защищённого `.runtime/blind-director/tokens.json` (JSON-объект case → access token, владелец текущий UID, mode 600) и выдаёт по запросу `case` и фиксированного `origin` одну строку JSON с теми же значениями и `access_token`. Оба конца проверяют UID peer. Токены и сокет не попадают в Git, консоль или клиентские журналы. Broker не запущен и токены не выпускались этой задачей; без действующих токенов и broker адаптер останавливается без Keychain fallback. Для фонового запуска сперва требуется бюджет проекта; в foreground процесс можно остановить штатно. Истёкший токен не обновляется автоматически.

Скорер для новых run поддерживает `no_alert`/`insufficient_data` только когда исход oracle допускает соответствующее решение. S7, S13, S14 и S6 требуют правильную причину и, если заданы, семейство и неделю; S14 дополнительно требует основную причину checkout. S12 может требовать честного отказа. Некорректный статус, пустой ответ, противоречие и нераспознанные поля остаются `unscorable`. Предыдущие frozen чаты и эталоны не изменяются и не пересчитываются как свежие; их старые хеши намеренно не соответствуют новой версии harness.

Новый генератор до исправления соседним владельцем нельзя подключать вслепую: некоторые его `warnings` раскрывают ответ. Подготовка новых наборов останавливается при обнаружении таких подсказок. Порядок работы: сначала единственный сквозной KES-кейс, затем S7/S13/S14/S6/S12.

## Проверка товарных названий и XLSX

`lint_inputs.py` сверяет label, SKU и продавца генератора с локальным проверенным экспортом Market Watch `.runtime/market-catalog/verified-app-offers.csv`. Проверяются JSON-наблюдения и контекст, все строки продажи, релизов и бэклога в XLSX, все XML-текстовые узлы книги, неподдерживаемые статусы, следы seed и известные подсказки ответа. S7 может использовать переименованный внутренний ключ только при наличии подтверждённого `canonical_product_key`; такие ключи учитываются отдельно. Lint читает только input, не vault. Harness выполняет его до выпуска набора для слепого прогона.

```sh
python3 tests/integration/blind_director/lint_inputs.py --inputs <private-output> --generator <generator-snapshot.py> --out <private-report.json>
GOMAXPROCS=2 GOFLAGS=-p=1 python3 -m unittest discover -s tests/integration/blind_director -p 'test_*.py'
```

`safe_for_blind: false` означает карантин: пакет не загружают в Airlock. Проверка базируется на локальном экспорте, её точность зависит от его охвата и даты; числовые ряды остаются синтетическими.
